# lixiang-secretary · 用理想汽车财报训练一个「董秘」

《学会使用大模型》第三课 · 方向 B 作业。

一句话目标：把理想汽车历年财报做成问答对，用 LoRA 微调一个小模型学会董秘的答话口径，
再用**四格对照 + 知识库对照**证明它到底学会了什么、没学会什么。

流水线：`data/build_qa.py`，三角色同一个 DeepSeek 模型靠提示词分工。
切块 114 块（9.1 万字）→ 每块 3 问 → 逐条作答 → 逐条质检。

| 指标 | 数值 |
|---|---|
| 生成问答对 | 342 条（171 秒） |
| 质检：有据满分 | 341 |
| 质检：小出入 | 1 |
| **质检：编造** | **0** |
| 自动筛选保留 | **264 条** |
| 丢弃 | 78 条（开头即拒绝 35 / 整条只说材料未涉及 29 / 正文混入繁体 14） |
| 训练池 / 测试池 | **213 / 51** |
| 表格块 / 叙述块 | 101 / 163 |

丢弃的三类都不是"答错"，而是"没东西可答"：表格块里问"为什么"（必然只能答材料未涉及）、
以及 14 条正文漂回繁体（口径要求是正文简体、引用照抄繁体）。

### 口径约定（本项目的关键设定）

- **原文 = 繁体**（港交所中文版原貌），引用时用「」一字不改
- **问题与回答正文 = 简体**
- **依据格式**：`【依据：《理想汽车_2025年报》第 6 页】`，报告名必须与真实文件名逐字一致
- 信息不足时**必须**写「材料未涉及」，不许编造

### 质检字段

`qc_review.csv` 里每条留了模型打分 + 人工复核列：

`有据(0/1/2)` · `自然(0/1)` · `简体` · `编造` · `引用名一致` · `自动筛选` · `丢弃原因`
→ 后接 `人审-有据` / `人审-自然` / `人审-处理` / `人审-备注` 四列**留空待填**（作业要求的抽检留痕）

## 第 6 步：人工抽检表

`data/make_qc_sample.py` 分层抽 60 条（训练池 45 + 测试池 15，跨 11 份报告、
覆盖表格块 23 / 叙述块 37），并做一层**自动预检**：

> 把答案里出现、原文里找不到的数字单独标出来。
> 引用「」里的数字必须能在原文找到（**硬错误**）；
> 正文里的数字可能是推算出来的，如用收入/成本算毛利率（**合理**）。
> 另外会剥掉【依据…】再比，否则页码会被误判成数字。

自动预检结果（60 条）：

| 类别 | 条数 |
|---|---|
| 引用数字对不上原文（硬错误） | **0** |
| 正文出现推算数字 | 17 |
| 无异常 | 43 |

17 条推算数字逐条核过，全部正确（毛利率、同比增减额、增长倍数、占比等）。

**产出**：`qc_sample.csv`（在 Excel 里填）· `qc_sample.md`（对着屏幕审，含折叠的原文摘录）

### 机器复核与总表回填（2026-10-12 补）

批改要求"人工抽检"在提交物里**看得见**。原来的问题是：60 条抽检表里
`有据 / 数字 / 处理` 三列人工填好了，但「自然」没审过；342 条总表
`qc_review.csv` 的人审列设计上留空待填，打开容易被误判成"没做抽检"。

补法（`data/machine_review.py`，**各是各的、不冒充人审**）：

| 动作 | 结果 |
|---|---|
| 独立机器复核「自然」（全量 342 条，与原始质检**不同提示词**） | 自然 274 / 生硬 68；**保留池 264 条一致率 96%**；不一致几乎全落在已被剔除的拒绝型回答上 |
| 抽检 60 条机器复核 | 判「自然」57 / 60 |
| `qc_sample.csv` 追加 | `机器复核-自然`、`机器复核-理由` 两列（列名写明是机器复核） |
| `qc_review.csv` 追加/回填 | 「抽检」标记（60 条）+ 人工三列按 qa_id 回填 124 格 + 机器复核列；**`人审-自然` 保持为空**，留给本人 |

复核用的是独立口径的提示词（复核明细 `machine_review.csv`，原始返回在
`data/cache/` 可离线核）；口径里明确写了"本项目的引用格式要求不算生硬"——
第一版提示词没写这句，把"照抄原文附页码"误判成不自然（342 条里误伤了 72 条），
修正后重跑。**复核口径也是要校准的**，这本身就是个教训。

## 第 6.5 步：来源页审计 + 造数据留痕（2026-10-12 补）

批改要求补「来源页」和「造数据」。数据里其实每条都写了 `doc / page_start /
section`、回答里也带 `【依据：《…》第 N 页】`——但**没人逐条核对过它们是不是
真的对得上**。"写是写了"和"核过了"是两回事，这节把后者做出来。

**`data/audit_sources.py` → `source_audit.csv`（342 + 140 条全量逐条）**，
三条检查与判分器同源（共用 `quote_check.py`）：报告名是否与来源一致、
依据页码是否对上（±1）、每个「」引文能否在来源页原文逐字找到。

| | 生成集 342 条 | 评测集 140 条 |
|---|---|---|
| 依据报告名与来源一致 | **342 / 342** | **140 / 140** |
| 依据页码与来源一致（±1） | **342 / 342** | **140 / 140** |
| 引文在原文逐字可查 | **373 / 375 句** | **170 / 170 句** |
| 引文在原文查无 | 2 句 | 0 句 |

查无的那 2 句都是**表格页把表格改写成了叙述句**（数字自表格、句子是自己组的，
如"資產總值 162,349,078"——原表里这两个词中间隔着 4 个年份列）。
不再是"数据对不上"，但逐字不算数，明细里与真编造分列——差在哪一眼看得见。
审计时还发现 3 条**漏写【】**的"依据：《…》第 N 页"：格式分照扣，
引用分按内容照算（依据的判定看内容，不看括号）。

**`data/make_provenance.py` → `provenance_report.md`（造数据留痕）**：
挑 3 条代表（叙述块 / 表格块 / 测试池），从 API 缓存里把生成链**完整重放**——
原文 → 提问提示词 → 原始返回 → 作答提示词 → 原始返回 → 质检提示词 → 原始返回
→ 入库记录（含保留/剔除决定）。每条都做**重放核对**：用缓存重新解析出的
问题/答案/质检必须与 `qa.jsonl` 逐字一致（3 条全部 ✅，报告里逐条标了）。
所有 2,076 个原始返回都在 `data/cache/`（键 = 请求载荷 sha256 前 32 位），
**可离线复核，不依赖任何后续接口**。

## 第 3 步（续）：四格评测集

`data/build_paraphrase.py` 生成换问法：

|   | 原问法 | 换问法 |
|---|---|---|
| **训练过的报告** | `trained_original` | `trained_rephrased` |
| **没训练过的报告** | `untrained_original` | `untrained_rephrased` |

- 前两格用训练池抽出的 **30 条探针**——**它们本来就进训练集**，这是刻意的：
  原问法考"记住没有"，换问法考"是背题面还是记住了事实"
- 后两格用测试池 **40 条**，绝不进训练集
- 换问法只换措辞不换事实，且**不得比原问题泄露更多答案数字**
  （生成后自动复查，泄露则重试；实测 70 条零泄露）

**产出**：`eval_grid.jsonl`，共 **140 条**（30 / 30 / 40 / 40）

## 第 5 步（上）：判分器 `eval/judge.py`（格式 / 事实 / 引用 三维）

**先冻死判分标准，再去训模型**——否则就是事后挑标准。

**2026-10-12 按批改意见拆成三个维度**：原来「引对报告」混在格式分里，
微调模型编造带引号的原文时格式分照拿满分 —— 拆开之后：

| 维度 | 分值 | 怎么算 | 裁判 |
|---|---|---|---|
| **格式** | 0–2 | ① 有【依据：…】 ② 有非空「…」引用 —— **只看有没有，不判真假** | 规则 |
| **事实** | 无独立分 | 关键数字净命中（题干回声剔除）+ 第三方模型判 0/1/2 | 规则 + 模型 |
| **引用** | 0–3 | ① 依据报告名对 ② 页码对（±1） ③ **所有「」引文在 1,449 页原文里逐字可查** | 规则 |

两种事实分并行，因为它们各有盲区（数字全中但结论说反了 → 客观满分、主观 0）。

**引文溯源怎么查**（`data/quote_check.py`，判分器与审计共用同一份逻辑）：
全语料归一化拼成大字符串，引文（含省略号的按段拆开）逐句回查，分四档 ——
**逐字**（只差空白）、**去标点**、**繁简**（引的是简体，口径缺陷但不是编造）、
**未命中**（编造或改写）。「逐字/去标点」才算引文为真；繁简单独记列，
不冤枉也不放过。实测这条尺子是准的：**参考答案自己的引文 170/170 全部逐字可查**，
而微调模型的引文 128 句里 126 句原文查无。

**自检**（`--selftest`）：拿参考答案当预测 → 数字命中全 100%、引文 0 编造；
拿别的题的答案冒充 → 数字全 0%。判分器通过自检，不是橡皮图章。

### 一个坑

`eval_grid.jsonl` 里每条题在**原问法 / 换问法两个格子里各出现一次**，
所以索引键必须是 `(qa_id, cell)` —— 只用 `qa_id` 会把一半数据吃掉。

## 第 5 步（下）：生成器 `eval/generate.py`（Colab 上跑）

三条路线对着同一套 140 条题各答一遍：

| arm | 是什么 | 对应 |
|---|---|---|
| `base` | 原始基座，不给上下文 | 训练前知道多少 |
| `sft` | 基座 + LoRA，不给上下文 | 微调后写进权重的有多少 |
| `rag` | 基座 + 检索到的原文片段 | 「A 的知识库 + 同一个小模型」 |

**检索**：作业 A 要求「向量 + BM25」，所以两条都上，用 RRF 融合，默认 top-8。
`--retriever bm25|embed|hybrid`，bm25 纯标准库、可离线验证，embed/hybrid 在 Colab 上跑。

BM25 单条的实测命中率（正确页落在 top-k 内，±1 页容差）：

| 格子 | top-5 | top-8 |
|---|---|---|
| 训练过 · 原问法 | 67% | 70% |
| 训练过 · **换问法** | **53%** | **57%** |
| 没训练过 · 原问法 | 75% | 80% |
| 没训练过 · **换问法** | **70%** | **75%** |

注意换问法那两格明显更低 —— 这正是课程讲的「**BM25 说法一变就漏**」，
也是为什么要加上向量检索。

### 预期结果

| arm | 预期 |
|---|---|
| `base` | 两格都接近 0 —— 基座不知道理想汽车的财报数字 |
| `sft` | 训练过的两格高，没训练过的两格**仍然接近 0** |
| `rag` | 四格都能答（每次都读得到原文），但答话格式不如 `sft` 像董秘 |
| `sft_rag` | 口径与知识都齐 —— 四条里唯一"三条腿都齐"的 |

**这就是结论**：微调学的是「怎么答」，知识还得靠检索递进来。

| **四格平均** | 0.3% | 1.0% | 26.3% | **38.3%** |

**格式分**（0–3，答得像不像董秘）

| 格子 | 基座 | 微调后 | 建库 | 微调+建库 |
|---|---|---|---|---|
| 训练过 · 原问法 | 0.00 | 2.27 | 0.00 | 1.43 |
| 训练过 · 换问法 | 0.00 | 2.50 | 0.00 | 1.23 |
| 没训练过 · 原问法 | 0.00 | 2.45 | 0.00 | 1.60 |
| 没训练过 · 换问法 | 0.00 | 2.25 | 0.00 | 1.48 |
| **四格平均** | 0.00 | **2.37** | 0.00 | 1.44 |

**五条结论**：

1. **微调给的是「口径」，不是「答什么」**。格式分 0.00 → 2.37，净命中仍 ≈1%。
   而且**口径能迁移**：完全没训练过的报告上，格式分仍是 2.45 —— 学到的是格式，
   不是那 30 页的内容。
2. **知识完全来自检索**。`建库` 用的是**没微调过的基座**，只是把检索原文塞进提示词，
   净命中就有 26%。这些百分点没有一个来自模型「记住」。
3. **两条轴几乎正交，合起来最好**。微调 × 检索交叉后净命中 38%，高于任一单条 ——
   微调还顺带提升了模型「利用检索结果」的能力。
4. **反直觉的副作用：检索会挤掉口径。** `微调+建库` 的格式分（1.44）明显低于
   纯 `微调后`（2.37）。因为检索进来的原文片段自己就是用 `【报告名 第 N 页】`
   包的，模型看到就模仿这个格式，不再用训练时学的 `【依据：…】`。
   **「把资料喂进去」和「让它按规范说话」是会互相干扰的。**
5. **最危险的一类错误：格式完美、内容全错。** 微调模型会在编造的数字外面套上
   毫无破绽的「原文引用」和页码。实测同一条回答里，开头写「同比增长 207.8%」，
   紧接着引用的原文却写着「增加 203.1%」——**引文内部自相矛盾，格式分却是满分**。
   这类错误比直接答错更难被发现。

# 踩坑记录

跑这个项目实打实花掉几个小时才弄明白的事，记下来免得重来。

## 序号一：训练把模型练成了复读机（2026-10-06）

第一次完整跑通后，判分出来的四格**全是 0%**。这不是「模型没学会」，是模型坏了。

**症状**：微调前基座回答正常，微调后输出变成「下面是小」重复 500 多遍，
140 条预测里没有一条正常回答。

**怎么定位的**：

1. 三条路线（base / sft / rag）**同样坏** → 不是某条路线的问题，是共用的环节
2. 检查 LoRA 权重：无 NaN/Inf，ΔW 范数均值 0.41（正常范围）→ 不是梯度爆炸
3. 复读次数 508–511 ≈ `max_new` 的 512 → 模型把同一个 token 吐满上限
4. 用户回报「微调前正常、微调后复读」→ 据此判断是训练把权重练坏了
   ——**这个判断后来被证明是错的**：权重好好的，问题出在训练之后的推理态

**真正的原因：推理前没把模型切回推理态。**

`prepare_model_for_kbit_training()` 会打开**梯度检查点**，它和 KV cache 互斥
（HF 会把 `config.use_cache` 置为 False）。训练结束后模型仍停在训练态，
此时直接调 `.generate()` 就吐出复读——**而权重其实是好的**。

改成训练后显式复位（notebook 里的 `to_inference()`）：

```python
model.gradient_checkpointing_disable()
model.config.use_cache = True
model.eval()
```

**走了两条弯路，记下来免得再走**：

1. 先怀疑 LR 太大（2e-4 + alpha=2r），降到 1e-4 + alpha=r —— **没用**
2. 再怀疑 unsloth 打补丁打坏了 —— 结果 **unsloth 根本没装上**，走的是标准 peft

**排除法的关键三个数**：训练 loss 0.5–1.5（正常收敛）、权重无 NaN/Inf、
ΔW 范数 0.41（正常）。**三项都正常却说训练把模型练坏了——这个矛盾本身就在
提示：坏的不是权重，是权重之外的东西。**

**顺带修掉的其它缺陷**（不改的话四格表本身是错的）：

- **`disable_adapter()` 还原不干净**：原设计是训练完再关掉 LoRA 跑 base 路线，
  实测还原失败。改成**训练之前**先跑 base 和 rag（那时 B 矩阵还是零初始化，
  模型就是纯基座）。
- **`max_new=512`** → 192；`generate()` 里强制 `padding_side='left'`。
- 精度统一 fp16（T4 是 Turing 架构，无 bf16 硬件支持）。
- 超参也顺手收敛了：LR 1e-4 / alpha=r / 2 轮。

**加了体温计**：训练前后各问一次「1+1 等于几」。
**答得出 → 权重是好的，问题在推理态；也复读 → 权重真坏了。**
这一个问题就能把两类原因分开，比猜快得多。

**加了自检**：训练后立刻检查演示输出是否复读，是就报错中止，
不再白跑 140 条预测。**下次跑只要看到这行红字，就知道问题复现了。**

## 序号二：提示词被悄悄截断，提问正好在被砍掉的那一头（2026-10-06）

**症状**：`rag` / `sft_rag` 两条路线答非所问——输出的是一段繁体财报腔的续写，
没有 `【依据】`、没有 `「」` 引用，**而且全程不报错**。

**原因**：`generate.py` 里写死 `max_length=3072`，而 RAG 的 system 提示词要
塞 6000 字原文（≈5,500 token）。`truncation=True` 是**从后面截**，
而提问正好在最末尾——**模型压根没看到问题**，只好顺着上下文继续写财报。

**为什么难查**：`base` / `sft` 的提示词短，躲过了这个 bug。于是现象看起来像
「只有带检索的两条路线坏了」，极易误判成检索坏了。实测先后误判为
①向量精度问题 ②system 提示词写法问题，各白跑一轮。

**修法**：`--max-len` 默认提到 8192，并在真的发生截断时打印警告。

**连带**：T4 上没有 Flash Attention，注意力显存 ≈ batch × 头数 × 长度²，
长度翻倍显存四倍，`--batch` 必须从 8 降到 4。

**教训**：提示词拼好之后应该先断言「问题那句话还在里面」，
而不是等模型答非所问再回头找。

## 序号三：bf16 权重在没有 AVX512 的 CPU 上慢到不可用（2026-10-07）

**症状**：CPU 上给 1431 页建向量索引，10 分钟连**一批**（32 页）都没跑完。

**原因**：`Qwen3-Embedding-0.6B` 的 `config.json` 里写着
`torch_dtype: bfloat16`。`AutoModel.from_pretrained()` 不显式给 `dtype`
就**按 bf16 加载**——而本机是 i7-10870H（Comet Lake），
**只有 AVX2，没有 AVX512、没有原生 bf16**，torch 只能走模拟实现。

```python
dtype = torch.bfloat16 if self.device == "cuda" else torch.float32
AutoModel.from_pretrained(model_name, dtype=dtype)      # ← 这个不能省
```

**实测**（同一台机器，都是 32 页 × 512 token 一批）：

| dtype | 一批 | 全量 1431 页 |
|---|---|---|
| bf16（默认加载出来的） | 10 分钟没跑完一批 | 数小时 |
| **fp32（显式指定）** | **79 秒** | **59 分钟** |

**为什么难查**：不报错、不掉精度，**只是慢**。而且 `generate_local.py` 里
生成模型是显式给了 `torch_dtype=torch.float32` 的，唯独向量这一步漏了，
所以看起来像「检索器本身就很慢」，很容易去优化错的地方。

**教训**：CPU 上跑任何 HuggingFace 模型都要**显式写 dtype**——
checkpoint 里记的 dtype 是按 GPU 写的。

## 序号四：向量模型的下载是截断的，而「文件非空」骗过了下载脚本（2026-10-07）

**症状**：`generate_local.py` 报
`Error while deserializing header: incomplete metadata, file not fully covered`。

**原因**：上次下载到一半关机，落盘的是**非空但截断**的 `model.safetensors`
（1,089,036,288 字节，真实大小 1,191,586,416，缺 98 MB）。
而 `download_models.sh` 当时只判断 `[ -s "$out" ]`（文件非空）就跳过，
于是这个残缺文件一直冒充「已下载」。

**修法**：下载脚本改成**和远端字节数比对**（HF 会 302 到 CDN，要取最后一条
`content-length`），对不上就用 `curl -C -` 续传，下完再核对一次。

**为什么难查**：报错信息指向「模型文件坏了」，看起来像模型本身有问题；
而且四条路线里只有带检索的两条用到它，又容易被当成检索逻辑的锅。

**附带**：原先 `EmbedIndex` 一旦加载失败，只打印一句
「退回 BM25 单独跑，不影响流程」——这是**错的**：hybrid 退化成纯 BM25
就换了一个实验条件，跑出来的「建库」一列和 README 写的不是一回事。
现在这种情况直接抛错中止。

## 序号五：装了 CPU-only 版 PyTorch，有显卡也一直没被用上（2026-10-07）

**症状**：带检索的两条路线一直在 CPU 上跑，105 秒/条，两条要 5 个多小时；
中途还因为整机内存紧张被系统回收了两次。

**原因**：本机有一块 **RTX 3060 Laptop（6 GB）**，`nvidia-smi` 一直正常识别，
但 `torch.cuda.is_available()` 恒为 `False`：

```
torch 版本: 2.14.1+cpu          ← 版本号里的 +cpu 就是全部答案
torch 编译时带的 CUDA: None
```

装的是 **CPU-only 轮子**。这不是「机器没有 GPU」，而是「装的 torch 用不了 GPU」——
**两者的表现一模一样**，所以极容易归错因。

**修法**：

```bash
python -m pip install "torch==2.14.1+cu130" \
```

**顺带补掉的两个只在 GPU 上才暴露的问题**：

1. `generate_local.py` 是照 CPU 写的，`from_pretrained` 之后**没有 `.to(device)`**。
   就算装了 CUDA 版 torch，权重默认仍留在 CPU —— **照样在 CPU 上慢慢跑**。
   已补上，并加了 `torch.cuda.empty_cache()`（6 GB 卡得省着用）。
2. GPU 上模型是 bf16，而缓存里的向量是 fp32，`self.emb @ q` 直接报
   `addmv input tensors must have the same dtype`。CPU 上两边都是 fp32，
   所以这个 bug 只在换到 GPU 后才露头。已统一到 fp32 再点积。

## 序号六：显存分配器碎片把 GPU 拖到假死，而占用率还显示 100%（2026-10-07）

**症状**：`sft_rag` 在 3060 上跑到第 5 条突然变慢（22 秒 → 173 秒），
第 6 条**直接卡死 12 分钟没有任何输出**。而 `nvidia-smi` 全程显示
**GPU 利用率 100%、频率 1942 MHz、温度 76 °C** —— 看着像满载在算，
实际一个字都没吐出来。

**为什么 `sft_rag` 中招、`rag` 没事**：两条跑的是同一个模型、同样的
ctx 6000。区别在**输出长度** —— `rag`（基座）平均只生成 ~100 token，
`sft_rag`（微调过）每条都会吐满 192 token 的引文。多出来的 KV 缓存和
中间激活把显存水位从 ~4.6 GB 顶到 5.7 GB（总共只有 6.1 GB），
分配器碎片正好在这个临界点上把路堵死。

**修法**（不动任何实验配置）：

```bash
PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True
```

显存占用立刻从 **5,718 MiB 降到 4,629 MiB**，速率稳定在 ~16 秒/条，不再退化。

**怎么快速分辨「真在算」和「假满载」**：看**磁盘上的产出有没有往前走**。
`generate_local.py` 逐条落盘，所以 `preds/*.part` 的行数和日志里的条数
是唯一可信的进度信号 —— **GPU 占用率在这里会骗人**。

**顺带**：这是「逐条落盘」第三次救场（前两次见序号四、序号五）。

## 序号七：交付的笔记本"有输出"和"真跑过"是两回事（2026-10-12）

**批改原话**：「所交笔记本未保存运行输出，不能只凭结论验收。」
根因很直白：训练一直在 Colab / Kaggle 上跑，结果靠下载 zip 带回本地，
**`train/lixiang_lora_sft.ipynb` 这个文件本身从没被真正执行过** ——
24 个格子的 `outputs` 全是空数组。结论再多，验收的人看不到形成过程。

**解法**：notebook 改成平台自适应的一份文件，再用 `train/run_notebook_local.py`
（nbclient）在本机真执行、真存输出。这一轮踩到的坑，按疼的程度排：

1. **把 LoRA 合并进 4bit 权重，等于把微调抹掉。** `merge_and_unload()`
   先把 nf4 反量化、加上 LoRA 增量、再量化回 nf4 —— 增量本来就只占
   百分之几，**重量化直接把它吃掉了**。实测合并后 sft 的输出与
   **没微调的基座逐字相同**（前三条回答一模一样），董秘格式整个消失。
   合并确实快 3 倍、省 1.2 GB（10.0 → 3.2 秒/条，四组对照在
   `_scratch/bench_peft.py`），但这个快法买的是一辆没有发动机的车。
   **4bit 基座上的适配器只能挂着用，不能合。**
2. **6 GB 卡上，`CUDA driver error: device not ready`（"Failed to create
   GPU mapping"）在内存一紧张就会出现。** 崩了两次（一次在生成、一次在
   训练起步），都是别的程序把显存/内存挤紧的时候。它不报 OOM、不给你
   降批的机会，直接让 CUDA 上下文报废。对付办法：**每格落盘**（崩了
   最多丢一格）+ 生成兜底（撞上就清显存、降到批量 1 重试）。
3. **长任务被强杀时，连 `except/finally` 都来不及跑。** 第一版执行器
   只在结尾把 notebook 写盘 —— 跑了一小时被系统按内存压力杀掉，
   **0 个输出**，白跑。改成**每跑完一格就落盘一次**，现在最多丢一格。
   （「逐条落盘」第四次救场，这次轮到 notebook 自己。）
4. **nbclient 的 `on_cell_complete` 是"执行请求刚发出"时调用的**，
   不是完成时。拿它打进度，日志会显示「第 15 格完成」而磁盘上的
   预测文件还没影。要用 `on_cell_executed`（输出都收完了才触发）。
5. **挂着 LoRA 生成，比裸模型慢 3 倍。** 每一层都要在 4bit 主权重之外
   多走一遍 LoRA 计算（fp32 权重、现场转 dtype），长提示词尤其吃亏：
   同一批 4,700-token 提示词，裸模型 3.6 秒/条，挂 adapter 10.0 秒/条。
   把权重转 bf16 没用（9.3 秒/条）—— 开销不在 dtype，在那条额外的
   计算路径上。**所以带检索的两条路线在本机各要一小时，排时间按实测
   的持续吞吐量算，别按短测数字拍。**

## 生成预测慢的三个原因（改完快 5–10 倍）

```python
tok.padding_side = 'left'                     # ① 解码器批量生成必须左填充
FastLanguageModel.for_inference(model)        # ② 关掉为训练开的梯度检查点
max_new_tokens=192                            # ③ 别设 512
```

第 ③ 条最坑：**基座模型不会输出 EOS**，`max_new_tokens=512` 会让它每条都
硬生成满 512 个 token 才停。140 条 × 512 = 7 万 token 白烧。

配套：`batch=16`、打印「已完成/总数 + 预计还需多少秒」，不然只能干等着猜。

## Qwen3-Embedding 的三个坑

```python
self.model = self.model.to(self.device).eval()   # ① 必须搬到 GPU
last = enc["attention_mask"].sum(dim=1) - 1      # ② 取最后一个 token 池化
v = h[torch.arange(h.size(0)), last]
dtype = torch.float32 if device == "cpu" else torch.bfloat16   # ③ 显式给 dtype
```

① 漏了不报错，只是慢几十倍（1431 页 fp32 在 CPU 上实测 59 分钟）。
② **取第一个 token 不会报错，但向量质量是坏的**——这个坑最隐蔽。
③ 不给 dtype 就按 `config.json` 里的 bf16 加载，**在没有 AVX512 的 CPU 上
慢到不可用**——见「踩坑记录 · 序号三」。

查询侧加英文指令前缀官方称还能涨 1–5%：

```python
"Instruct: Retrieve passages from a Chinese company's financial report "
"that answer the question\nQuery: " + query
```
